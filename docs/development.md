The human partner's VM also hosts other projects and services. Keep unrelated resources available throughout the work.

## Tools and build

Use Node.js 24 or newer. `rust-toolchain.toml` selects Rust 1.99.0 and the WebAssembly target.
WebAssembly is a portable compiled form for browsers and Workers.
Morphology runs in TypeScript, separately from that binary.
Its Peggy grammar and generated parser live in `packages/morphology`.
The repository limits Rust builds to two parallel jobs. The WebAssembly build script also uses two jobs.
The generated bindings require `wasm-bindgen-cli` 0.2.105 to match the Rust dependency.

Use compatible Ubuntu packages through `apt` when the task needs a system tool.
Use `npx` for compatible npm tools when necessary. Keep project dependency versions pinned.
Do not install packages for another distribution into this VM. Do not replace shared system libraries for a prototype dependency.
Use the smallest task-relevant privileged action. Keep existing VM services usable.

If the matching binding tool is absent, install it through Cargo:

```sh
cargo install wasm-bindgen-cli --version 0.2.105 --locked --jobs 2
```

Run the build from the repository root:

```sh
npm ci
npm run build
```

`npm ci` installs the locked npm packages. The build produces WebAssembly bindings, the standalone server bundle, and browser assets.
The outputs are `packages/core/generated`, `apps/server/dist`, and `apps/web/dist`.
The repository ignores these reproducible outputs.

The core build accepts `CARGO_TARGET_DIR` and `JVC_WASM_BINDGEN`.
The first variable selects Rust build storage. The second names the exact `wasm-bindgen` executable.
Its version must remain 0.2.105.
For this VM, use a task-specific target directory:

```sh
CARGO_TARGET_DIR=/build/jbovlacku/targets/prototype npm run build:core
```

Use established cryptographic libraries. Do not implement curve arithmetic in application code.
Keep dependency notices with redistributed files. The [dependency guide](dependencies.md) describes the required notices.
The project software license remains a prelaunch choice.
New native definitions use the [CC0 contribution terms](format.md#remaining-body-fields). Imports retain their source rights and attribution.

## Morphology tools

`packages/morphology` implements word recognition, segmentation, lujvo construction, and gismu generation in TypeScript.
These tools need no WebAssembly initialization. The public core facade reexports their existing API names.
The [profile guide](morphology.md) defines historical compatibility and the current Peggy profile.

The repository commits both the grammar and its generated parser. The browser loads ordinary generated JavaScript without string evaluation.
From the repository root, regenerate the parser and run its tests:

```sh
npm run build:morphology
npm run test:morphology
```

The tests make sure that the generated bytes match the grammar and the pinned compiler.
They include the ported Rust tests, versioned profile controls, and gencmu word cases.
Gismu calculations use exact BigInt fractions. The builders retain work and conflict-detail limits.
The browser checks author-entered word forms. Server admission keeps morphology separate from record validity.

The compatibility harness compares every result with a separately compiled Rust baseline at revision `62340e6`.
Before a comparison, restore that revision into a task-specific scratch directory and compile the retained oracle there.
Use the same task target directory for Cargo. Never restore the baseline over an implementation checkout.
The source for that oracle is `scripts/morphology-oracle.rs`.
Copy it into the baseline crate as `crates/jvc-morphology/examples/morphology-oracle.rs` before compilation.
The harness requires explicit read-only dictionary and reference paths. Its command help describes those inputs:

```sh
npx tsx scripts/compare-morphology.ts --help
```

Keep comparison data and measurement logs outside the repository. The harness records input digests, operation counts, and exact differences.
It compares analysis, segmentation, construction, scoring, generation, and structured resource failures for every retained profile.

## Standalone app

The Node.js adapter serves the API and built browser assets. It stores objects, receipt state, and SQLite indexes in its data directory.
A new directory starts empty. The adapter requires no Cloudflare credentials or network access to Cloudflare.
Keep the data directory across process restarts when persistence matters.

Start the built application from the repository root:

```sh
JVC_DATA_DIR="$PWD/.cache/node" npm run start:built
```

The application listens on `127.0.0.1:8789`. Its readiness endpoint is `/api/health/ready`.
Stop the foreground process with Ctrl+C. SIGINT and SIGTERM close the service and its SQLite databases.
`npm run start` runs the TypeScript source instead of the built server bundle.
Build the WebAssembly bindings before either command.

The Node adapter accepts these environment variables:

| Variable                    | Purpose                                                                                       |
| --------------------------- | --------------------------------------------------------------------------------------------- |
| `JVC_DATA_DIR`              | Persistent objects and SQLite databases. The default is `data/node` relative to the checkout. |
| `HOST`                      | Listen address. The source default is `127.0.0.1`.                                            |
| `PORT`                      | Listen port. The default is `8789`.                                                           |
| `JVC_ASSETS_DIR`            | Browser assets. The source default is `apps/web/dist`.                                        |
| `JVC_SERVER_ID`             | Service identifier. The source default is `local-node`.                                       |
| `JVC_VIEW`                  | Explicit selected view event ID. A fresh service has no dictionary view.                      |
| `JVC_STATE_TRAVERSAL_LIMIT` | Explicit state work budget from 1 through 1,000,000,000. It overrides the saved import limit. |
| `JVC_PUBLIC_ORIGIN`         | Explicit public origin permitted to submit browser writes through a reverse proxy.            |
| `JVC_SNAPSHOT_LIMIT`        | Retained snapshot count. The default is 16. Allowed values are 1 through 64.                  |
| `JVC_CORS_ORIGINS`          | Comma-separated additional permitted origins.                                                 |
| `JVC_POLICY_URL`            | Operator policy URL. The prototype placeholder is not a published policy.                     |
| `JVC_PROTOTYPE_BATCH`       | Set `enabled` only for authorized local batch fixtures. The default disables batch admission. |

A browser write is allowed when its `Origin` equals the request URL's origin.
Set `JVC_PUBLIC_ORIGIN` when an HTTPS reverse proxy gives the browser a different public origin.
Other browser origins need explicit `JVC_CORS_ORIGINS` entries.
The adapter does not infer the public origin from forwarded headers.
Browser assets allow local scripts and WebAssembly. They block inline scripts, JavaScript string evaluation, and framing.

The coordinator keeps the most recent 16 distinct snapshot wrappers by default.
Use `JVC_SNAPSHOT_LIMIT` on Node or `SNAPSHOT_LIMIT` in the Worker configuration to change this count.
Expired or unpublished snapshot reads return HTTP 410 with `snapshot_expired`.
Signed envelopes, bodies, selections, and accepted event cursors remain durable after wrapper expiry.
Reusing an identical retained snapshot ID refreshes its retention position.
A wrapper becomes visible only in the transaction that publishes its current pointer.

An older prototype database has no trusted snapshot publication order.
Migration from the first prototype retains its current snapshot only. Other old snapshot IDs expire.
A rebuilt inventory must match the stored current pointer. A mismatch reports storage unavailable.
Legacy object-store wrappers and the old snapshot-ID table remain as one-time cleanup debt.
Anonymous event and selection admission has no contributor quota. Signed object retention remains unbounded.

A generation is an index copy for one snapshot. An alias points to a generation with the same entries.
The Node search index retains its current generation, one rollback generation, active staged generations, and the source generations that aliases use.
Index publication removes obsolete rows, aliases, and markers in the same SQLite transaction.
Historical API reads use immutable packages. If an index base is absent, the service rebuilds it from the completed package entries.

This prototype needs an admission policy and resource limits before public use.
New admissions store wrappers in bounded coordinator rows and create no more legacy wrapper objects.

At most two distinct evaluation jobs and two package jobs run at once.
Requests for the same snapshot and view share evaluation work.
An evaluation keeps its cache slot until its package publication finishes.
An unknown or invalid requested view is rejected before full evaluation.
Alternate views cannot evict the most recent configured-view evaluation.
If a committed admission cannot obtain an evaluation slot, its receipt still reports the durable acceptance and cursor.
It reports unavailable interpretation with `evaluation_resource_unavailable`. A later receipt read or retry can evaluate it.

The Node adapter evaluates new snapshots in separate worker threads.
A worker thread runs code independently within the same process. At most two evaluation runtimes remain live.
One runtime serves completed rankings while another reads stored compact records and evaluates the next snapshot.
The browser and Cloudflare Worker keep the same shared core and inline evaluation path.
Without an explicit snapshot, word, search, identity, account, and package reads use the last completed snapshot.
The manifest also names that completed snapshot. Interpreted results name their snapshot and view.
Raw replication reads can expose the newer accepted inventory and name its snapshot.
Ordinary own-history loads use the manifest's completed snapshot, including loads on word, person, and trust pages.
Only final own-history scans before handover, compromise, and acceptance recovery select the accepted snapshot.

Lifecycle safety scans discover a peer's accepted snapshot through the first unpinned identity-heads page.
They pin later head pages, activity pages, and signed envelopes to that snapshot.
The activity request uses `accepted=1` and requires the response marker `history: "accepted"`.
This mode skips evaluation and returns unavailable interpretation for every listed record.
A peer that ignores this mode cannot supply a complete accepted-history scan to the browser.

If a pinned read returns HTTP 410 with `snapshot_expired`, the browser starts the scan again from a fresh accepted snapshot.
Each scan has at most three attempts under its original time and work limits.
The browser discards evidence from an expired attempt before another attempt.
Repeated expiry reports incomplete history and blocks the signature. It does not classify the peer as malformed.

Handover and acceptance recovery use this history before signing.
Online compromise previews also include configured peers and refresh their history after an unlock wait.
A changed preview clears the user's approval before a new lifecycle signature.
These scans cover each peer's observed accepted snapshot. They do not prove that no unseen concurrent record exists.

The accepted cursor advances after durable admission. The materialized cursor advances after evaluation, packages, and index publication complete.
During that gap, a new event receipt reports `index_lag` and `evaluation_pending`, with unavailable interpretation and a null snapshot.
A late-body receipt also uses a null snapshot until the completed snapshot contains the same body mapping.
An unchanged event keeps the completed snapshot and its derived receipt while later writes wait.
This receipt lets the browser finish its wait without waiting for every other write.
If a completed snapshot contains the exact event representation without a derived receipt, the receipt names that snapshot with `evaluation_unavailable`.
The receipt rebuilds a missing evaluated session before it answers.
The service retains the preceding completed snapshot during a backlog. Failed jobs leave it available, and later reads retry the latest inventory.

After local publication, a fresh browser word read waits for accepted records from this server to finish evaluation.
The page shows that the server stored the records while its word view updates.
This page session tracks only receipts whose envelope and required body match the saved delivery.
The wait lasts at most 15 seconds and stops when the reader leaves the page.
A temporary network failure or HTTP 5xx response triggers another poll within that same deadline.
A failed wait keeps delivery accepted and offers a refresh. Ordinary reads and explicit snapshot reads still use their completed snapshot.

After a profile publication, the profile page uses the same wait before it requests the current claim.
The page bypasses its cached profile and shows a pending notice during the wait.
If the wait fails, the page offers a profile refresh without another signature.
Personal recomputation waits before it requests the manifest for the next snapshot.
The manifest lists that snapshot's inventory and packages.
Cancellation stops these waits without removing accepted delivery evidence.

A checkpoint is a saved evaluated state.
The Node adapter keeps one pinned checkpoint under `evaluation-cache` in `JVC_DATA_DIR`.
The file contains compressed Node binary data for evaluated results and search packages. It contains no original envelopes or compact record inputs.
An independent SQLite row pins its digest and calculation context.
That context includes the exact snapshot, logical inventory, event position, selected view, work limits, and Wasm artifact digest.
The pin also retains one private base wrapper. This wrapper does not extend public snapshot retention.

The core also compares its checkpoint schema and binding before restore.
Missing, damaged, incompatible, or incorrectly bound checkpoints return to evaluation from private compact records.
The cache limits are 256 MiB compressed and 768 MiB decoded. A cache failure does not change protocol results.

Startup can restore a valid older checkpoint after a crash.
The adapter requires the same selected view, work limits, and core version, and the exact saved base inventory.
It restores record inputs from the private compact store, then reads new or changed compact records from the latest inventory.
The core applies its ordinary rules for incremental updates and full rebuilds from retained authenticated records.
If the pin differs from the durable materialized snapshot, startup uses it only for calculation, even when public retention still includes it.
Startup does not publish that base's index or mark it as completed.
Without a current completed state, interpreted reads wait for catch-up. Recovery never moves the served snapshot or its materialized cursor backward.
An expired private base also supports calculation only and remains unavailable through public snapshot routes.

Shutdown stops admission and closes idle connections immediately.
Active responses close their connection after their bytes finish. Idle keep-alive sockets do not delay checkpoint work.

The adapter allows up to ten seconds for core evaluation, then closes stalled client connections.
Before stopping any evaluation worker, it prevents further publication and saves the latest completed snapshot from its owning worker.
This save bypasses the normal capture interval, even while another worker rebuilds a newer accepted snapshot.
Durable handlers and file operations can extend shutdown beyond ten seconds.

The adapter closes SQLite and releases the data directory lock after those handlers and file operations settle.
Accepted records and the last valid checkpoint remain available for startup recovery.
Checkpoint recovery rebuilds a missing search index from the saved entries before readiness.

The service captures at most one checkpoint per minute after a 100 ms quiet period.
It keeps only the latest pending snapshot during that interval. A failed capture also counts toward the interval.
A failed live core export can retry once immediately. This bounded retry is an exception to the capture interval.

Shutdown bypasses the interval and saves the latest completed state before stopping its worker.
Core evaluation, checkpoint export, and checkpoint restore run in evaluation threads.
Binary serialization of the enclosing checkpoint, package construction, and SQLite operations still use the main thread.
The capture interval limits serialization frequency, not its duration.

Use a separate data directory for each test service. Do not point a disposable test at another service's database.
A selected view and explicit import selection determine which imported publications appear.
The [importer guide](../packages/importer/README.md) describes local signed proposals and their disposable key inputs.

### Initial Lensisku data

The importer reads pinned REST captures and PostgreSQL COPY snapshots under one canonical Lensisku source origin.
Both extraction commands share one journal for that origin and importer key.
The SQL extraction uses every source definition language that the format can represent.
It preserves authored source fields and available history. It omits derived vectors and caches with explicit source limitations.
Malformed related rows leave affected definitions unresolved. They never create false source removals.
Split COPY fragments retain their first readable owner and remain malformed, including breaks in different fields.
Missing lookup rows block only their dependent definitions.
The importer guide describes both extraction commands, source manifests, and unresolved reports.

SQL extraction uses a calibrated disk estimate before signing and reports measured proposal bytes afterward.
It counts definitions that need new publications before estimating carrier growth and added space for the loaded copy.
Observation growth still covers all staged definition rows.
The normal estimate includes a projected loaded copy, while `--check-existing` covers only its scratch proposal and staging.
That check reparses the source with retained envelopes and refuses new publications.
Use a new scratch directory with a copied journal. The command refuses existing `carriers.jsonl` or `source-archive` paths before opening the journal.
Its 1.5 GB budget does not authorize a service load.

After preparing a signed proposal, stop the Node server for the target data directory.
From the repository root, load the proposal into that directory:

```sh
npx tsx packages/importer/src/load-cli.ts \
  --proposal .cache/import-sql \
  --data .cache/node \
  --state-traversal-limit 1000000000
JVC_DATA_DIR="$PWD/.cache/node" npm run start
```

The loader admits signed carriers, their import selection, and their selected view.
It records the selected view and explicit traversal budget in `loaded-view.json`.
Node startup reads that file. `JVC_VIEW` and `JVC_STATE_TRAVERSAL_LIMIT` provide explicit overrides.
A repeat load reuses accepted event positions. It does not create new signatures.

The loader and Node server hold an exclusive `.node-data-lock` in the target directory.
If a process leaves that lock, settle the process before removing its exact lock directory.
Keep the proposal journal and external source archive available for retries and source inspection.
The SQL archive records the digest and path of the external dump instead of copying it into the proposal.
Rights remain unknown in this extraction. Local loading grants no publication authority.

Large imports need a larger explicit state work budget and enough memory.
The traversal flag changes the work limit only. It does not remove memory or event limits.
The loader completes admission before the server builds its snapshot, indexes, and search packages.
The SQL loader projects only final changed event bindings and stages at most 256 compact records per batch.
One admission transaction promotes staged rows and accepted events together. Failed admission removes its own staged rows.
The Node server and top-level loader clear abandoned stages only while they hold the exclusive data directory lock.
Generic test coordinators without SQL staging retain changed projections in memory.

Successful admission alone does not establish successful dictionary evaluation.

The server trusts its private storage. Admission checks signatures, body hashes, and canonical JSON before it stores each record.
The offline loader uses the same admission checks. It stores each compact record in the transaction that stores the accepted event.
A compact record contains the fields that state evaluation and search packages use.
Its key includes the event ID, envelope hash, body mapping, and extraction format version.
Preferred signature changes and late or shared bodies create matching compact records in that same transaction.
Old compact records remain available for historical snapshots. Original envelopes and full bodies remain available for replication and reads.

Every server evaluation uses these stored compact records. This includes cold starts, view changes, core upgrades, and checkpoint fallback.
These paths do not repeat signature checks, body hashing, or full body parsing.
The core uses a separate host-only port to accept the trusted projections. The browser continues to authenticate original records.
Browser source imports the public `browser.ts` facade, which exposes no private record insertion, extraction, or restore ports.
A source-policy test rejects host ports and direct runtime imports under `apps/web/src`.
The shared raw Wasm artifact still contains host exports. The facade and source policy define the browser application boundary.

No API route exports the private compact records as verification evidence.
The server reconstructs exact canonical envelope text from each stored header, event ID, and decoded SSHSIG blob.
Admission requires canonical base64, so this reconstruction preserves every signature variant and snapshot hash.
Cold evaluation and checkpoint restore fill the envelope cache from these private fields.
The first admission after a restart or Worker eviction needs no retained envelope reads.

An extraction format or body-validation change requires another projection of existing data.
Compact extraction version 5 and semantic extraction version 2 apply the `fuhivla` lexical kind.
Earlier derived rows require backfill before reuse. Original signed records remain unchanged.
Missing or older compact records trigger a parse-only backfill from private original bytes.
Backfill does not repeat signature checks, body hashing, or canonical JSON checks.
It preserves invalid body schema diagnostics. It commits at most 256 rows per batch and reads at most 16 records at once.
The native golden test pins the complete projection output to `HOST_RECORD_VERSION`.
Its immutable fixtures live under `crates/jvc-runtime/tests/fixtures` with a separate digest file for each extraction version.
A projection change requires a new version and golden digest. The test covers all body statuses, action kinds, and both publication projections.
It includes legacy account evidence and attribution fields that the two projections retain differently.

A stored projection that fails the extraction decoder emits `verified_record_decode_failed` with its event and binding.
The server rebuilds that row from trusted original bytes and replaces the derived projection without another signature or body hash check.
`verifiedRecordStatistics` exposes missing-row, decode-failure, and backfill counts for tests and diagnostic callers.
Tests inspect committed rows directly before evaluation so automatic backfill cannot hide an admission defect.

To complete backfill before startup, stop the service for that data directory and run this command:

```sh
npx tsx packages/importer/src/backfill-cli.ts --data .cache/node
```

The command requires an existing data directory and coordinator database before it takes the lock.
The command holds the same exclusive data directory lock as the server and loader.
A repeat run skips records with the current extraction format version.
Ordinary startup also fills missing compact rows as evaluation needs them.
Storage damage is outside this trust model. Restore private records and original objects from a trusted backup after such damage.

The persistent checkpoint stores evaluated results separately from these private records.
Checkpoint restoration loads record inputs from the compact store. A core or view change discards results and keeps those records.
A transient worker fork still transfers its complete private runtime state between threads. This transfer is not the persistent checkpoint.
Sessions retain evaluated state instead of all source bodies. Small ancestor sets use sparse storage.
Identical history caches share storage when the snapshot contains no acceptance events. Work charges stay unchanged.

When the event limit is exceeded, the core returns `resource_unavailable` before it builds ancestry caches.
It retains authenticated records so that a later limit change can recover them.

New snapshots reuse authenticated compact records and the preceding evaluation.
A complete issuer with one active key can update a judgment register or publish a native definition without a full rebuild.
The new event cannot resolve an old missing reference. The evaluator also requires enough work for the equivalent full result.

Trust, lifecycle, view, account, status, rafsi, profile, report, and bridge changes rebuild state from the retained authenticated records.
Changed bodies, import selections, calculation configuration, or unavailable history also force a rebuild.
These rules follow the [history and authority rules](format.md#4-causal-order-and-acceptance) and the [ranking rules](format.md#8-editorial-trust-and-ranking).

After checkpoint restore, a mixed batch with any global action constructs ancestry once for its full rebuild.
An unavailable restored base also constructs ancestry once.
The rebuilt evaluation and work budget match full evaluation. Diagnostic statistics omit discarded incremental work.
An unavailable base reports `base_unavailable`.

Forks share immutable ancestor payloads. After 64 appended records, a rebuild incorporates the new IDs into the ancestor universe.
The evaluator retains the full logical work charge. Uncertain work at an ancestor-width boundary forces a rebuild.

Judgment updates can return a patch of at most 1 MiB for the exact parent session.
The facade applies that patch to immutable result maps. Other changes return the full result.
Differential tests compare the complete state and ranking with full evaluation.
The external Lensisku slice test is ignored in an ordinary Cargo test run.
It requires a local file of signed carriers through `JVC_LENSISKU_CARRIERS`.
If you request this test without that variable, the test fails with a setup message.

From the repository root, run the external test with the carrier file that your task authorizes:

```sh
JVC_LENSISKU_CARRIERS=/absolute/path/to/carriers.jsonl \
  cargo test -p jvc-state --test incremental \
  lensisku_slice_mixed_writes_equal_full_evaluation -- --ignored --exact --nocapture
```

Search packages reuse authenticated text and attribution fields from unchanged records.
New admissions pass the original validators. Server package builds reuse stored compact projections. Stored objects remain immutable.
Judgments reuse package parts and search entries. Changed publications rebuild the affected language packages.

Missing and late body mappings retain their separate handling. Browser builders cache at most 1,024 validated public keys.
Every newly admitted signature and every browser signature check passes the point, scalar, embedded-key, and equation rules.
The existing combined-request API remains available for smaller browser snapshots. It still allocates the complete request.

## Native carrier tools

The native `jvc` command supports canonical directory carriers, committed Git trees, JSONL carriers, and envelope-only streams.
A carrier is a portable snapshot of records and selections.
The [carrier guide](../crates/jvc-carrier/README.md) describes the file layout, validation, refusal policy, and operational read limits.

Print the supported native interface from the repository root:

```sh
cargo run -p jvc-runtime --bin jvc -- --help
```

Use `cargo run -p jvc-runtime --bin jvc --` before the arguments below.
The table names the implemented interface. Output files and directories must be new.

| Arguments                                                              | Behavior                                                                                           |
| ---------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| `canonicalize FILE`                                                    | Write canonical JSON to standard output.                                                           |
| `verify FILE`                                                          | Inspect one signed envelope and report signature, action, and body availability.                   |
| `evaluate FILE`                                                        | Evaluate a runtime input object containing events, bodies, a selected view, and import selections. |
| `validate DIRECTORY`                                                   | Inspect canonical carrier files, signatures, body schemas, hashes, and the manifest.               |
| `validate-git REPOSITORY COMMIT`                                       | Read and inspect exact blobs from a local committed tree.                                          |
| `validate-checkout REPOSITORY COMMIT`                                  | Also make sure that checkout files match the committed blobs.                                      |
| `inventory DIRECTORY`                                                  | Report the snapshot, logical inventory digest, and manifest.                                       |
| `import FILE --format jsonl --output DIRECTORY [--selection FILE ...]` | Import canonical records and separately supplied import selections.                                |
| `export DIRECTORY --format jsonl`                                      | Write canonical records to standard output. It omits import selections.                            |
| `merge LEFT RIGHT --output DIRECTORY [--policy FILE]`                  | Write the authenticated set union with an explicit local refusal policy when supplied.             |
| `retain DIRECTORY --policy FILE --output DIRECTORY`                    | Write a filtered carrier and its resolved policy sidecar.                                          |

JSONL carriers contain `{body,envelope}` records. Export sorts them by event ID.
A JSONL export does not include import selections. Keep each selection as a separate canonical JSON file.
Supply every required selection through repeated `--selection FILE` arguments when importing.
This restores the complete carrier snapshot. Importing records alone cannot restore a snapshot that contained selections.

An envelope-only stream contains one signed envelope per line without inline bodies.
`validate`, `inventory`, `export`, and `merge` accept this separate format through `--format envelope-jsonl`.
Envelope validation reports signature and action results. Its report explicitly states that causal evaluation was not requested.
It does not establish full dictionary conformance.

Git commands require a full commit object ID. They never fetch remote data or select a branch by arrival order.
Keep the input directory stable during a read. The Git reader avoids hooks, filters, lazy fetch, and global configuration changes.
The full target `jvc` catalog remains larger than the implemented command surface.

Refusal policies contain `refused_bodies`, `refused_events`, and `refused_issuers` arrays.
They remain private local policy. The carrier does not adopt a peer's refusal policy.
`retain` and a policy-bearing `merge` write `OUTPUT.retention-policy.json` beside the output directory.
The sidecar contains the resolved policy. Refusing a known event records its issuer so that later merges can retain the refusal.

Keep that sidecar beside the output directory, outside the public carrier.
If either local input has an adjacent retention-policy sidecar, a merge without `--policy` refuses to continue.
Use `merge --policy FILE` to select the refusal policy explicitly. That selection can intentionally override the saved policy.
Removing the sidecar loses this check. A filtered directory alone does not remember refusals, and a later merge can restore content from its other input.
A refusal does not prove physical deletion from Git history, peers, or backups.
If a write fails, treat partial output as unusable until inspected.

A reservation is a cost estimate held before job admission.
The service constructs each possible task's actual initial provider request, including its prompt and tool schema.
Let `B` be that request's UTF-8 byte count. Each byte counts as one input token.
Let `M` be the task output cap, `Pi` the input price, and `Po` the output price.
The response cap is `R = 262,144` bytes. The feedback allowance is `F = 32 × 512 × 6 + 4,096 = 102,400` bytes.
The correction bound is `C = 2R + F = 626,688` bytes. It includes echoed reasoning, tool arguments, and escaped feedback.
For tasks after a generated frame, add `G = 2R + 4,096 = 528,384` bytes. Other tasks use `G = 0`.
Each task reserves three possible answers with a safety margin of two:

```text
reservation(task) = 2 × sum(a = 0..2) [ (B + G + aC) × Pi + M × Po ] / 1,000,000
reservation(job) = sum(reservation(task))
```

The operation determines which tasks remain. An absent initial frame includes the places task and up to sixteen generated places.

Before admission, every server and network allowance must cover existing charges plus the new reservation.

Each network receives one quarter of each configured server limit by default: 8 USD per hour and 40 USD per day.
At least four separate network shares are needed to fill a server spending window.
IPv6 requests count against both their /64 and /48 allowances. One IPv4 address has one allowance.
The durable ledger stores keyed SHA-256 hashes of these units. It stores no client address or prefix.
A private random key remains stable across restarts. Legacy records with no network identity count against every network until their windows end.

The initial provider request is bounded at 2,097,152 bytes before any generated-frame allowance.
Generated-frame follow-up tasks add at most `G` bytes to that bound.
A conservative four-task ceiling uses the largest task cap for every task and adds `G` to all three follow-up tasks:

```text
ceiling = 4 × 6 × ((2,097,152 + 626,688) × 0.10 + 20,480 × 0.20) / 1,000,000
        + 3 × 6 × 528,384 × 0.10 / 1,000,000
        = 7.5866112 USD
```

The exact reservation depends on the actual prompts, input, and tool schemas. Model prices remain separate from spending allowances.

A request above any empty allowance or the optional per-job ceiling returns `billing_request_too_large` without `Retry-After`.
Its message explains that waiting cannot help. Reduce the request or raise the named operator allowance.
A temporary spending refusal returns HTTP 429. For settled charges, `billing_limit` includes the computed `Retry-After` seconds.
The calculation projects each blocking record's expiry and chooses the earliest time that clears every exhausted allowance.
An active job can still report a missing or larger cost. Such a refusal uses `billing_pending` without a promised retry time.
The response explains that active work holds the allowance and that its final charge remains unknown.
When no pending cost can alter the release, the service uses the actual reservation release or charge expiry.
An active charge uses the job deadline as the latest possible answer time before its hourly or daily window starts.
The service never reduces `max_tokens` to spend a remainder. Accepted jobs finish even if reported costs exceed their reservations.

Each reported turn cost replaces that turn's estimate when the job settles.
If a paid turn reports no cost, its charge remains twice the sum of its input estimate and full output allowance.
The log leaves unknown provider usage unknown. A transport failure also retains that turn's estimated charge.
While a job runs, admission counts the larger of its complete reservation and accumulated charges.
When every answer reports a cost, completion releases the unused reservation. Otherwise the complete reservation remains within the spending window.
The last paid answer sets the spending window for all charges in that job.
Every turn sends `usage: { include: true }`, including correction turns.
[OpenRouter's usage guide](https://openrouter.ai/docs/cookbook/administration/usage-accounting) says that this field is deprecated because usage is automatic.
The field does not guarantee a usage report.

Node stores the cost ledger in `assistance-spending.sqlite` within `JVC_DATA_DIR`.
The Worker stores it in the existing admission Durable Object. It splits snapshots into 64 KiB binary parts with a checksummed manifest.
One storage transaction replaces the parts and manifest together. A failed write preserves the preceding complete snapshot.
Reservations reach durable storage before any provider request.
A restart keeps interrupted jobs' outstanding reservations until their spending windows expire.
Recovery starts those windows at the later of the restart time and the stored job deadline.
A legacy record without a deadline uses the restart time. The lost job cannot report its final cost.
The ledger contains cost records, network hashes, and its private hash key. It contains no draft text or provider credential.
An unreadable or unwritable ledger blocks new assistance jobs.
The same ledger also controls host embedding calls through `AssistanceService.embed`.
An embedding query uses the caller's network limits. Operator index and probe batches use the server limits.
Query callers must supply a valid IP address, a normalized IPv6 /64, or the trusted local host marker `local`.
All these operations share the server's hourly and daily limits and execution slots with generation.
The existing Node key file and Worker key binding also serve embedding requests.
An invalid or empty `JVC_AI_EMBEDDING_*` value disables embedding alone on both hosts.
The host emits a fixed warning that names the invalid field. Generation profiles and remembered browser consent stay unchanged.

Each embedding batch permits one through eight inputs, with at most 4,096 UTF-8 bytes per input and 32 KiB in total.
Inputs already include the exact profile prefix. The adapter rejects malformed UTF-8 and preserves the remaining bytes.
Encoded requests permit 64 KiB. Provider responses permit 2 MiB.
The adapter pins the model and Nebius route, disables fallback and redirects, and makes no automatic retry.
The embedding input price must be positive. The route price cap uses the lower of that price and `JVC_AI_MAX_PRICE`.
It accepts the exact returned model names `qwen/qwen3-embedding-8b` and `Qwen/Qwen3-Embedding-8B`.
The adapter rejects invalid input indices, dimensions other than 4,096, and nonfinite or zero vectors.
It produces unit-normalized float32 vectors.

An embedding reservation quotes 32,000 input tokens per input at the configured embedding price.
At the default price, one input reserves 0.000320 USD. Eight inputs reserve 0.002560 USD.
This conservative quote covers provider normalization without assuming that original byte counts bound token counts.
A reported cost replaces that estimate. An unknown sent charge keeps the estimate through the normal spending windows.
Invalid vectors or a model mismatch never remove a reported charge.
Financial failures and model mismatch use separate error codes. Later profile services must handle compatibility state.

The embedding deadline covers admission, key loading, transport, response reading, and settlement preparation.
During admission, a caller's abort signal prevents dispatch and removes any unsent reservation.
After admission completes, a caller's abort signal detaches its response. The server continues key loading, the request, and settlement.
At the deadline, the caller stops waiting. A transport that ignores abort keeps its execution slot until it ends.
This prevents replacement requests from creating unbounded concurrent transport work.
`AssistanceService.embeddingOperations` returns at most 64 diagnostic records, with active operations first.
The records expose operation IDs, purpose, deadline, transport state, and spending estimates without input text or credentials.
After restart, reservations remain charged and appear as retained operations.
An operation that was active at restart has unknown cost and retains the larger of its reservation and accumulated charges.
Retained records do not establish whether an earlier request completed or lost its transport.
Every error after an embedding reservation names its operation through the error's `operation` field.
An operator can inspect these records and request a new bounded attempt through the same service after a limit clears.
The earlier charge remains. A stuck transport requires its completion or a service restart before its slot returns.
Job pause, resume, and explicit retry links belong to later indexing work.

These host methods expose no browser route. Semantic search remains disabled until storage and query services pass their tests.
Compatible query caching and current-view filtering also belong to those later services.
At most 16,384 cost records remain within a day. Reaching this bound also refuses new jobs with a retry interval.
On a later admission, the service combines completed operator batches with known costs into hourly summary rows.
Queries, generation jobs, errors, and unknown charges keep their individual rows.
A summary ages from its latest charge, so earlier charges can stay counted for up to one extra hour.
Summaries retain the operator's spending identity and count against server limits. They consume no client network share.
Recent batch diagnostics keep the individual charge and link to their summary through `summary`.
An aggregate diagnostic has `aggregated: true`. Restart retains the financial summary without claiming individual batch outcomes.
Mocked tests run two complete indexes of 59,129 inputs each, retain 8,192 assistance history rows, and admit another generation job.
The ledger keeps its existing row limit, 32 MiB Worker storage bound, and atomic 64 KiB parts.
A local workerd test measured a valid maximum ledger with escaped 128-character IDs and two hashes per record.
Its JSON occupied 17,858,669 bytes. The old single stored value occupied 6,324,340 bytes.
The split form used 273 parts. Its largest stored part occupied 65,549 bytes, including serialization overhead. The manifest occupied 112 bytes.
The test restored the complete ledger after a runtime restart. An injected write failure preserved the preceding ledger.
Local workerd accepted the oversized old value. This does not remove the hosted 2 MB value limit or prove hosted quota compliance.
These estimates require accurate operator prices. They do not guarantee charges from an untested compatible provider.

The log bounds use separate size allowances. The initial request allowance is `B = 2,097,152` bytes before generated-frame additions.
The HTTP body permits 262,144 bytes, and loaded definition context permits 131,072 bytes.
A generated initial frame comes from a response of at most 262,144 bytes.
Existing frames permit 256 places. A compound permits 64 components, each with at most 256 supplied place indices.
The mapping legend groups indices by spelling. The tool schema does not repeat the permitted names for every answer key.
The feedback allowance is `F = 102,400` bytes. The correction allowance is `C = 2 × 262,144 + F = 626,688` bytes.

An individual provider response has a 256 KiB limit. Each job reserves at most 64 MiB for its serialized inference log.
Before a provider turn, the service reserves space for that request, the complete bounded response, and its displayed log fields.
If the next turn cannot fit, the job fails with `log_limit` before it sends that turn.
The request allowance is `4 × (3B + 3C)`, about 31.17 MiB for all twelve turns.
Five response copies per turn add 15 MiB. Four exchange headers and their initial text add at most 8 MiB.
The 64 MiB limit leaves room for feedback, checks, usage, and log metadata above these 54.17 MiB allowances.
Generated-frame follow-up tasks add at most `12G = 6,340,608` bytes across request copies and exchange headers.
The combined allowance remains below 61 MiB and leaves room within the 64 MiB limit.
These are serialized bounds. They are not a JavaScript heap bound.
Request snapshots share immutable messages and tool schemas. Exchange text shares the initial request strings.
Raw response fields and correction metadata stay as compact JSON and expand one field at a time when read.
Job reads stream JSON rather than build one complete response string. Admission counts each completed attempt without serializing the whole log again.
Node retains at most four private logs. The Worker retains at most two and runs at most two jobs at once.
Thus retained logs represent at most 256 MiB on Node or 128 MiB on the Worker when fully serialized.
The compact shared representation uses less memory. Wasm, dictionary state, an active provider response, and serialization still need separate headroom.
These local bounds do not prove that every admitted dictionary and job combination fits a hosted Worker memory limit.
A full reservation returns HTTP 429. Saving or dismissing a result releases its reservation through acknowledgment.

`GET /api/v1/session` returns a CSRF token and sets a Secure, HttpOnly, SameSite=Strict session cookie.
The browser sends the token in `X-CSRF-Token` for `POST /api/v1/assist` and `DELETE /api/v1/jobs/ID`.
Private requests use the configured `JVC_PUBLIC_ORIGIN` on Node or `PUBLIC_ORIGIN` on the Worker, or the request origin by default.
Extra origins permitted for public dictionary reads cannot use private jobs.
Each session can start 12 jobs per hour. Each client network bucket can start 48 jobs per hour.
One bucket holds at most eight sessions and one retained job. A failed job with no provider turn releases its retained slot.
A new visitor can replace the oldest idle session within a full bucket.
A parsed request protects its session during context loading and admission. Running jobs and readable retained results also protect their sessions.
The service limits body reads to ten seconds. A body that exceeds that time returns HTTP 408 with `request_timeout`.
Slow uploads never protect their sessions from idle eviction.
Dismissed and discarded terminal records do not prevent idle eviction. Eviction removes their remaining job records.
At most 128 sessions exist at once. A new visitor can replace the oldest idle session at that limit.
`GET /session` refreshes a session for one hour. Job admission also extends it through the job's expiry.
Refreshing a session does not reset its hourly job quota.
Quota failures include a retry interval based on the exhausted limit.
A retained slot can last through the job deadline plus its reading window, capped by job expiry.
Capacity retry times include that window. Completion cannot extend the window beyond that bound.

Accepted work returns HTTP 202 with an opaque job ID, expiry, and polling interval.
Job reads expose the current task and answer count. Cancel aborts the outbound request and stops further local turns.
Cancellation cannot reverse an already transmitted request or a provider charge.
Private jobs expire after at most ten minutes. A service restart or Worker eviction also loses them.
Unknown and foreign job IDs return HTTP 404 with `missing`. Owned expired IDs return HTTP 410 with `job_expired` while their markers remain.
Expiry markers retain only the ID, owner session, and fixed expiry. Each session keeps at most 128 markers for at most one further hour.
Each session also keeps at most 128 unexpired job records. This separate limit returns HTTP 429 with `session_job_limit` and the earliest expiry interval.
Expiry markers never consume job slots. Reads and session renewal never extend either job or marker retention.
The job deadline leaves a final reading window of 60 seconds, or one quarter of a shorter test lifetime.
At the normal lifetime, a timeout occurs by nine minutes and leaves its failed state and log readable until expiry.
They use transient memory rather than the dictionary object store, indexes, receipt journal, or ordinary logs.

The browser saves a terminal result with its draft, then sends `DELETE` as an acknowledgment.
Until acknowledgment, expiry, or two minutes after completion, the service holds the result so a lost response can be read again.
After that reading window, the service discards the result and log and releases its retained slot.
Later job reads return HTTP 410 with `result_discarded`. The browser explains that the result was discarded and that the author can ask again.
Acknowledgment preserves the terminal state and discards the result and log. It does not cancel a completed action.
The browser keeps the durable log copy. Publication and peer synchronization omit that log.
The browser stores each retained log as JSON text before it copies or saves the draft.
It decodes logs for display and exports their original public JSON shape with the shared iterative serializer.
Raw JSON exports preserve the exchanged payload fields, except server credentials and encrypted reasoning.
The service removes those fields before a response or correction request leaves the inference runner.
The browser limits ordinary API responses to 16 MiB and private job reads to 96 MiB.
Each response wait lasts at most 30 seconds. An action expires after 15 minutes in the browser.
